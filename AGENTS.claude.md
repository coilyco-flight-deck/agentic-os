## Coily-managed lockdown files

`.claude/lockdown-deny.sh` and `.claude/settings.json` in every coily-using repo are regenerated by `coily lockdown` / `coily setup`. Different hosts and different coily versions routinely show them dirty, so they are **not** "user changes to leave alone." But an agent must **never stage or commit them** because they define a harness permission boundary. That boundary can only be widened from outside the agent operating under it, never by the agent rewriting the rules. So leave both files dirty, do not stage them, do not `git stash` around them, do not ask. Make your commit with only your own changes and let the dirty lockdown files sit in the working tree.

The canonical-bump is a **CI / human operation**, not an agent one. When coily's deny list changes, a CI job re-renders and commits the lockdown files across the catalog repos through a bot account. The files stay committed (never gitignored) so a fresh clone is fail-closed before `coily setup` first runs.
