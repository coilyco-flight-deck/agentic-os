# Features

What `agentic-os` does. Cross-platform shell, terminal, and secret-handling for every host Kai runs. Public, generic, leak-safe by construction.

This doc describes capabilities, not files. If you want a file inventory, run `ls`.

## Inventory

- [Shell and secret handling](features-shell-secrets.md) - cross-platform zsh, agent-CLI repo gate (claude/codex/opencode refuse to launch outside a git repo), in-process SSM secret loader, Warp terminal config, GPG-without-disk-passphrases and shared-key bootstrap, install surface.
- **Karabiner key binding assets** - `karabiner/*.json` store complex modifications symlinked into Karabiner's assets directory: Control+Escape -> backtick, a device-scoped left_option <-> left_command swap for the external keyboard, plus a command -> control remap scoped to Microsoft Remote Desktop so Cmd hotkeys reach the remote Windows session. Install `brew install --cask karabiner-elements`, setup in [docs/repo-layout.md](repo-layout.md).
- [Agents and sessions](features-agents-sessions.md) - agent self-name, session pulse, and a project-local status-line repo-checkout tracker ([`.agentic-os/statusline.sh`](../.agentic-os/statusline.sh)) that names the `org/repo` clones on disk which are not on an expected-repos list, i.e. the strays to remove.
- [Code review skill](../.agents/skills/tooling-code-review/SKILL.md) - the hand-curated in-container review stance for ward workers, with non-iterative diff review, baseline interpretation, and a stable pass/block output shape.
- [Which harness when](harness-selection.md) - the five agent harnesses (Claude, Codex, OpenCode, Aider, Goose) and three model tiers (trivial-local, capable-local, cloud), with a decision guide for picking one.
- [Test harnesses](test-harness.md) - one doc per agent probing a harness+model pairing before trusting it with real work. [Agent compatibility check](agent-compat.md) runs the daily unittest smoke; Goose also ships `ward exec goose-ask`.
- [Issue-corpus discovery index](issue-corpus.md) - `ward exec render-issue-corpus` renders the Forgejo issue corpus (every repo in `scripts/issue-corpus-repos.txt`, **open AND closed**, bodies + every comment) to one markdown file per issue under `corpus/` in the private `coilysiren/inbox` (which does **double duty** as both a corpus source and the corpus output host), so a warded container can **grep the corpus offline** to _locate_ an issue then confirm live state via `ward ops forgejo issue view`. A discovery index, not a source of truth: every file carries that disclaimer (the AGENTS.md anti-drift discipline). Incremental via `manifest.json` (skips issues whose `updated_at` is unchanged), all Forgejo I/O routes through `ward ops forgejo` (no `FORGEJO_TOKEN`), and trufflehog scans the rendered `corpus/` tree before the hourly `.forgejo/workflows/issue-corpus.yml` cron pushes it to inbox.
- [Forgejo Actions log streaming](forgejo-actions-logs.md) - the raw plaintext `ward ops forgejo actions logs` bridge for Forgejo's live web log route, layered onto the ward spec bundle because the upstream swagger omits the endpoint and the current renderer stays JSON-first.
- [ward deployment spec bundle](ward-specs.md) - the aos-hosted `ward` deployment input bundle for the coilyco fleet, and **the source of truth** for it. It carries the forgejo spec guardfile, the raw Actions log bridge overlay, the signoz and ollama guardfiles, the fleet manifest, and the smart-defaults bundle, authored here and consumed by ward through live `WARD_CONFIG_REF` selection that is stamped from the checked-out commit, not by rebuilding a custom binary from the release asset. The defaults resolve the fleet `direct-main` baseline and intentionally override the neutral ward PR default so `coilyco-flight-deck/ward` and `coilyco-flight-deck/agentic-os` stay on `pull-requests-and-merge`.
- [Cross-repo tooling and release](features-release-tooling.md) - pre-commit baseline, staged hygiene opt-ins, diagnostics, Forgejo-canonical release actions, and the reusable Telegram CI failure alert action. The release pipeline now computes the next tag, publishes and verifies the dev-base family by tier, and only then creates the tag and release so consumers never see a tag without a manifest. The public Forgejo-to-GitHub mirror contract is documented alongside it: Forgejo owns release/tag creation, GitHub mirrors `main` fast-forward-only, tags mirror append-only, and GitHub Releases stay opt-in only for a concrete downstream need.
- [Telegram CI failure alerts](telegram-ci-alerts.md) - composite `actions/telegram-alert` primitive for posting a red-channel Telegram alert on a failing job in `main`, with repo/workflow/job/ref/SHA/run URL context and no token leakage. The repo's own workflows inline the same payload to avoid local-action resolution drift on the mirror path.
- [Code review contract](../CODE-REVIEW.md) - the root review doctrine for repo-local invariants, historical issues, and refresh triggers, enforced by `check-code-review-contract`.
- [dev-base container image](dev-base-image.md) - the inner-loop toolchain: managed Pythons, pre-commit, node, go, Rust (`cargo`/`rustc`), .NET SDK 10 + ICU, Homebrew, aws cli, claude, mcporter, opencode, codex, goose, git-lfs, gh, helm, kubectl, yq, docker, tailscale, plus ward itself; the published family is split across `docker/dev-base/core|lang-node|lang-go|lang-dotnet|ops|agent|full/Dockerfile`, while the hidden ward builder stage stays inside `core` and `dev-base-full` stays the default. The image still bakes the dev-command surface, pre-commit and CI gate tools, a public substrate seed from the canonical `docker/dev-base/substrate-image-repos.txt`, in-container agent self-name and status line, git identity stamping, and the scheduled auto-bump workflow so the inner loop stays self-contained.
- [CI parity in dev-base](ci-in-dev-base.md) - the convention that every app's CI runs **inside the pinned dev-base image** through the same `ward exec test`/`lint`/`smoke` verbs a dispatched agent runs, so a green CI means "a headless agent can land this," not "it passed in some other environment." Pinned `vX.Y.Z`, never `:latest`, so adopting a newer image is a deliberate bump that re-validates every app. The aos-owned source of truth now derives from the tier folder layout through [`scripts/dev-base-build.py`](../scripts/dev-base-build.py), which turns `docker/dev-base/<tier>/Dockerfile` plus the release tag into the literal full ref at the same release tag; an ansible/template rollout templates that literal into each app (authoring-vs-rollout), never fetched downward at run time. Reference: [`ci-in-dev-base-example.yml`](ci-in-dev-base-example.yml) (agentic-os#328).
- [Managed AGENTS.md pointer block](features-agents-pointer.md) - org-aware, drift-checked workspace-base pointer rendered into each repo's AGENTS.md.
- [Encoded leak guard](leak-guard.md) - pre-commit hook that rejects plaintext occurrences of awkward-leak terms (employer/partner names, private-to-public references) held as hex and decoded only in memory, so the ruleset is not itself grep-bait.
- [Context-budget report](context-budget.md) - on-demand measure of the eager startup context each harness (claude/codex/opencode) loads vs a per-harness token budget, with per-source attribution, reusing the agent-compose resolution. Ships `immediate_walk` / `peripheral_walk` primitives (tracked-file count, bytes, chars/4 token proxy over `git ls-files`) that ward's role-aware three-tier probe (ward#373) consumes for the working-dir and reference-repo tiers.
- [Mount-eligibility manifest](mount-eligibility-manifest.md) - agent-compose emits `mount-eligibility.json`: per harness, the repos it may mount on this host (`~/projects/<org>/<repo>` paths plus an always-on default set), reusing the composer's scope/harness selection so ward reads the mount decision instead of re-deriving it. Drift-checked.
- [Committed ward-ops reference](ward-ops-forgejo-reference.md) - checked-in `ward ops forgejo describe` render so operator-verb names stay greppable, now including guarded workflow dispatch. `ward exec gen-ward-ops-reference` regenerates it. See agentic-os#261.
- [Catalog caps reference](catalog-caps-reference.md) - the `code-comments` / `documentation-layout` numeric caps rendered straight from the validator constants by `ward exec gen-caps-reference`, so docs and skills point at one generated source instead of hand-copying a number that drifts. `check-caps-reference-drift` fails commit on a stale render, mirroring `check-seed-skills-drift`. See agentic-os#284.
- [Tool-failure GlitchTip shipper](tool-failures-shipper.md) - `ward exec ship-tool-failures` drains the per-repo tool-use failure-record buffer (`~/.cache/agentic-os/tool-failures/<repo>.jsonl`, written by any harness producer) to GlitchTip: it gates on genuine failures (dropping classifier-`expected` benign non-zeros), sets the Sentry `fingerprint` to the record's own so a flood of identical failures collapses to one counted GlitchTip issue, tags by harness/failure_class/repo, and emits one Sentry-protocol envelope per failure past a per-file byte watermark (idempotent, resumes after a mid-file network error). The DSN is read once from SSM (`/sentry-dsn/tool-failures`, see [SSM.md](../SSM.md)) and fail-soft when absent - the buffer keeps accumulating - so the shipper lands DSN-pluggable before the GlitchTip project exists. Out-of-band (timer / SessionEnd hook), never a hot path. See agentic-os#250.
- [Canonical agent-id generator](dictatable-id-alphabet.md) - the cross-repo agent-naming primitives ward and cli-guard's Go port consume, homed in aos. [`agentic_os/agent_id.py`](../agentic_os/agent_id.py) generates a short **lowercase 2-letter+2-digit** id over the dictatable alphabet, with `new_id`, `normalize`, `is_valid`, and `seeded_id` backed by the committed vector contract. `org_shortnames.json` maps long Forgejo orgs to short container tokens, last-`-`-segment fallback. A drift test regenerates the vector and fails CI on staleness; `ward agent-id` prints a fresh id. See docs/dictatable-id-alphabet.md.
- [Knowledge-base freshness program](knowledge-base-freshness.md) - grades knowledge by **decay-class** (asserted/pointer/derived) and **half-life** (fast/slow), carried inline as `<!-- freshness: as-of= half-life= -->` provenance markers. `ward freshness` parses them across tracked docs and flags any fact aged past its horizon (`-- --check`), the loud trigger a scheduled probe (`.forgejo/workflows/freshness.yml`) fails on, since knowledge rot is silent where code drift is loud. Hermetic, time-based, not a commit-path hook.
